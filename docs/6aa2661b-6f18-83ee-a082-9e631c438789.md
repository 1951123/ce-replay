C_{\text{storage}}+

$$

视角。

## Statistics cost 可以看成一种 regularization

这点尤其漂亮。

刚才目标函数：

$$

\right]
$$

是不是非常像：

$$
\boxed{
\text{training loss}
+
\lambda\cdot\text{model complexity}
}
$$

在 ML 里：

$$
\min_\theta
L_{\text{train}}(\theta)
+
\lambda\Omega(\theta)
$$

在 statistics selection 里：

$$
\min_S
L_{\text{workload}}(S)
+
\lambda C(S)
$$

对应关系可以这样看：

| Machine Learning        | Statistics Management                  |
| ----------------------- | -------------------------------------- |
| training samples        | historical queries                     |
| data distribution \(D\) | workload distribution \(D_Q\)          |
| model parameters        | selected statistics \(S\)              |
| model complexity        | statistics 数量/大小/复杂度                   |
| training loss           | historical workload cost               |
| regularization          | statistics storage/maintenance penalty |
| overfitting             | 过度针对历史 query templates                 |
| test set                | future/unseen queries                  |
| generalization          | statistics 对新查询仍有价值                    |
| concept drift           | workload/data distribution 发生变化        |

所以从这个视角看：

> **限制 statistics 数量不仅仅是因为“磁盘贵”，它实际上还可能起到 regularization 的效果：阻止 statistics selection 过度拟合历史 workload。**

## 但这里有个和普通 ML 很不一样的地方

数据库的“训练样本”其实有**两个 distribution 在同时漂移**。

一个是：

$$
\boxed{D_Q:\text{ query workload distribution}}
$$

比如用户以前查：

```text

```

以后开始查：

```text

```

这是 **workload drift**。

另一个是：

\boxed{D_X:\text{ underlying data distribution}}
$$

例如：

```text

```

这是 **data drift**。

所以 statistics management 实际面对的是：

$$
\boxed{

+

}
$$

同时随时间变化。

这也解释了为什么 5.3.4 有两个看似不同的问题：

> **Which statistics to create?**

主要是在适应 \(D_Q\)。

> **When to update statistics?**

主要是在适应 \(D_X\)。

文档后半部分说，数据更新会使 statistics 随时间 obsolete，因此商业 DBMS 通常跟踪被修改的行数，在变化达到一定程度后重建 statistics。

用你现在的 ML 语言重新解释，就是：

$$
\boxed{
\text{Statistics Management}
=
\text{Model Selection under Workload Drift}
+
\text{Model Refresh under Data Drift}
}
$$

这个视角很强。

### 那“训练”是什么？

现在假设历史 workload 是：

$$
W_{\text{train}}
=
\{q_1,\ldots,q_n\}
$$

对于一个 statistics configuration \(\mathbf x\)，optimizer 在这些 statistics 下优化查询 \(q\)，产生：

$$
P(q;\mathbf x)
$$

我们可以定义 loss：

$$
L(\mathbf x)
=
\sum_{q\in W_{\text{train}}}
w_q C(P(q;\mathbf x))
$$

然后再考虑 statistics 自己的成本：

$$
\boxed{
\mathbf x^*
=
\arg\min_{\mathbf x\in\{0,1\}^m}
\left[
\sum_q w_q C(P(q;\mathbf x))
+
\lambda\sum_i x_i c_i
\right]
}
$$

其中 \(c_i\) 可以表示：

$$
c_i=
\text{storage cost}
+
\text{creation cost}
+
\text{maintenance cost}
$$

所以所谓“训练”，就是：

> **在历史 workload 上搜索一组最优的 0-1 statistics selection variables。**

这非常像 feature selection：

$$
\text{Feature Selection: }
z_i=1 \Leftrightarrow \text{选择 feature }i
$$

对应：

$$
\text{Statistics Selection: }
x_i=1 \Leftrightarrow \text{创建 statistic }i
$$

$$

$$

\begin{aligned}

\sum_{q\in W_{\text{train}}}
w_q C(P(q;\mathbf x))
\\
\text{s.t.}\quad&
\sum_i size_i x_i\le B\\
&
x_i\in\{0,1\}
\end{aligned}
}
$$

如果同时限制维护成本：

$$

就变成：

$$
\begin{aligned}
\min_{\mathbf x}\quad&
L(W_{\text{train}};\mathbf x)
\\
\text{s.t.}\quad&
\sum_i size_i x_i\le B\\
&
\sum_i maintenance_i x_i\le M\\
&
x_i\in\{0,1\}
\end{aligned}
$$

这样一看，它就很像 **knapsack / combinatorial optimization** 了。

如果：

$$

> 给每个 \(S_i\) 算一个 value，然后选 value 最大的几个不就好了？

通常没这么简单，因为 statistics 之间存在**交互作用**。

例如：


可能出现：

$$

$$

$$

$$

但：

$$

$$

甚至：

$$

$$

因为二者提供了大量重复信息。

```text

      ↓
同时修正两个 CE
      ↓
join order 改变
      ↓

```

所以真正的 loss 是：

$$
\boxed{L(x_1,x_2,\ldots,x_m)}
$$

而不一定能分解成：

$$
L=\sum_iL_i(x_i)
$$

这就是这个问题计算上很难的地方之一。

```text id="12an0a"
new query
    ↓
传统 optimizer
    ↓
使用学出来的 statistics configuration
    ↓
传统 CE
    ↓
Cost Model
    ↓
Plan
```

所以它**没有替换 CE**。

它优化的是 CE 的“知识库”。

---

# 3. 两者其实处于 optimizer pipeline 的不同位置

这是我觉得最关键的区别。

传统数据库：

```text id="utykmi"
                 Database
                    │
                    ↓
             Statistics
                    │
                    ↓
Query ───────→ Cardinality Estimator
                    │
                    ↓
                 Cost Model
                    │
                    ↓
               Plan Search
                    │
                    ↓
                   Plan
```

Query-based learned CE 是：

```text id="0g13l8"
Query
  │
  ↓
Learned CE Model  ←──── training workload
  │
  ↓
Cardinality
  │
  ↓
Cost Model
  ↓
Plan Search
```

而我们讨论的 learned statistics selection 是：

```text id="mq7jlh"
Historical Workload
        │
        ↓
Statistics Selection Learner
        │
        ↓
   Stats Configuration
        │
        ↓
Statistics ──────────────┐
                         ↓
New Query ───────→ Traditional CE
                         │
                         ↓
                      Cost Model
                         ↓
                     Plan Search
```

所以一个是在**学 estimator**：

$$
\boxed{Learn\ CE}
$$

另一个是在：

$$
\boxed{Learn\ what\ CE\ should\ know}
$$

这个区别很重要。

---

# 4. 两者的“参数”也完全不一样

Query-based learned CE：

$$
\theta\in\mathbb R^d
$$

例如 neural network weights：

$$
\theta=(w_1,w_2,\ldots,w_d)
$$

训练得到：

$$
f_{\theta^*}(q)
$$

属于典型的连续参数学习。

而 learned statistics selection：

$$
\mathbf x\in\{0,1\}^m
$$

属于：

$$
\boxed{\text{combinatorial model selection}}
$$

如果进一步学习 bucket 数、sampling rate 等：

$$
\theta=
(\mathbf x,\mathbf b,\mathbf r,\ldots)
$$

才变成 mixed discrete-continuous optimization。

所以两者虽然都叫 learning，数学问题其实很不同：

$$
\text{Learned CE}
\approx
\text{function approximation}
$$

而：

$$
\text{Learned Stats Selection}
\approx
\text{combinatorial decision learning}
$$

---

# 5. 最有意思的是：两者的 generalization 也不一样

假设训练 workload 全是：

```sql id="i9x8e0"
SELECT *
FROM R
WHERE A = ?
  AND B < ?;
```

突然来了一个没见过的：

```sql id="hdyh2b"
SELECT *
FROM R
WHERE A = ?
  AND C = ?;
```

### Learned CE 的问题

模型需要直接回答：

$$
f_\theta(A=?,C=?)
\rightarrow
\widehat{Card}
$$

即使 `(A,C)` 这种 query pattern 在训练集中没出现过。

所以它要求：

$$
\boxed{\text{query-to-cardinality function generalization}}
$$

如果 query encoding / model 没学到这种组合关系，就可能 OOD。

---

### Learned statistics selection 的问题

它不需要预测 cardinality。

它只需要之前选择：

```text id="k00kmu"
Stats(A)
Stats(B)
Stats(C)
Stats(A,C)
...
```

如果训练阶段保留了：

```text id="dvn0df"
Stats(A)
Stats(C)
```

那么即使从来没见过：

```sql id="p08je7"
A=? AND C=?
```

传统 optimizer 仍然可以：

$$
Sel(A=?\land C=?)
\approx
Sel(A=?)Sel(C=?)
$$

虽然可能因为 independence assumption 而不准确，但**至少整个传统 CE machinery 仍然工作**。

这带来一个潜在优势：

> learned statistics selection 学出来的是底层“数据摘要”，而不是直接记忆 query → cardinality mapping，因此它可能保留更多传统 optimizer 对 query structure 的组合能力。

但反过来也有缺点：如果真正重要的是：

$$
P(A,C)
$$

而训练 workload 从来没表现出 `(A,C)` 的重要性，selector 可能根本不会创建：

$$
Stats(A,C)
$$

于是新 workload 上还是会估错。

所以两边都有 OOD 问题，只是 **OOD 的形态不同**。

---

# 6. 一个非常漂亮的区别：一个学习“答案”，一个学习“证据”

可以这么理解。

Learned CE：

$$
\boxed{
q\rightarrow\widehat{Card}
}
$$

直接学习答案。

Learned statistics selection：

$$
\boxed{
W\rightarrow S^*
}
$$

学习未来回答 query 时应该准备哪些证据。

然后传统 CE 再根据这些证据推理：

$$
(q,S^*)\rightarrow\widehat{Card}
$$

所以有点像：

```text id="yzzyud"
Learned CE:
    学会做题

Learned Statistics:
    学会应该准备哪些参考资料
    +
    仍然让传统 optimizer 做题
```

这个类比其实挺准确。

---

# 7. 这导致二者的 inductive bias 很不一样

Learned CE 的 inductive bias 主要来自：

* query representation；
* model architecture；
* training loss；
* training workload。

而 statistics selection 的 inductive bias 很大程度来自**传统 CE 本身**：

```text id="g54cbk"
Histogram
NDV
MCV
multi-column stats
uniformity assumption
independence assumption
containment assumption
...
```

也就是说我们没有推翻几十年来数据库 optimizer 的结构，而是在问：

> **既然传统 CE 已经知道怎么利用 statistics，那么能不能用 workload 学习“哪些 statistics 最值得给它”？**

这是一个明显更 conservative 的设计。

---

# 8. 两者的 loss function 也值得对比

Learned CE 最自然的 loss 是：

$$
L_{CE}(\theta)
=
\sum_q
QError(
f_\theta(q),
Card(q)
)
$$

也就是说：

$$
\boxed{\text{预测 cardinality 准不准}}
$$

但 learned statistics selection 从 5.3.4 的思想出发，最好**不要**这么优化。

我们更希望：

$$
L_{Stats}(\mathbf x)
=
\sum_q
Cost(
Optimizer(q;\mathbf x)
)
+
\lambda C(\mathbf x)
$$

即：

$$
\boxed{\text{最终 plan 好不好}}
$$

这恰好对应文档强调的 statistics-selection 目标：寻找那些会显著影响 workload plan quality 的 essential statistics，而不是单纯让所有统计估计都尽可能准确。

于是出现一个非常有意思的区别：

$$
\boxed{
Learned\ CE:
\quad
Cardinality\ Accuracy
\rightarrow
Plan\ Quality
}
$$

通常是间接优化 plan quality。

而：

$$
\boxed{
Learned\ Statistics:
\quad
Statistics\ Configuration
\rightarrow
Plan\ Quality
}
$$

完全可以直接把 plan quality 当 objective。

---

## 9. 从 explainability / robustness 看，也有明显区别

可以做一个总结：

|                     | Query-based Learned CE    | Learned Statistics Selection |
| ------------------- | ------------------------- | ---------------------------- |
| 学习对象                | CE function               | statistics configuration     |
| 输入                  | query                     | workload                     |
| 输出                  | cardinality estimate      | statistics 集合                |
| 参数                  | 通常连续 \(\theta\)           | 主要是 \(x_i\in\{0,1\}\)        |
| 本质                  | function approximation    | combinatorial selection      |
| 替代传统 CE？            | 通常是/部分是                   | 否                            |
| 传统 histogram        | 可能不需要或辅助                  | 核心组件                         |
| optimization target | CE error 常见               | plan/workload cost 更自然       |
| 新 query             | model 自己预测                | 传统 CE 用 stats 推导             |
| 可解释性                | 取决于模型                     | 较强：知道创建了哪些 stats             |
| workload drift      | 可能 retrain model          | 调整 statistics configuration  |
| data drift          | model 可能需要 retrain/update | refresh statistics           |
| storage budget      | model size                | 很自然地成为 stats constraint      |
| 与现有 optimizer 集成    | 侵入较深                      | 相对温和                         |

---

# 10. 但还有一个更深的共同形式

其实两者最终都可以写成 statistical decision problem。

Learned CE：

$$
\theta^*
=
\arg\min_\theta
\mathbb E_{q\sim D_Q}
[
L(f_\theta(q),Card(q))
]
$$

Learned statistics：

$$
\mathbf x^*
=
\arg\min_{\mathbf x}
\mathbb E_{q\sim D_Q}
[
Cost(Optimizer(q;\mathbf x))
]
+
\lambda C(\mathbf x)
$$

区别就在：

$$
\boxed{
\text{一个学习预测函数 }f_\theta
}
$$

而：

$$
\boxed{
\text{一个学习决策配置 }\mathbf x
}
$$

因此后者严格来说甚至更接近 **decision-focused learning**：

> 我不要求中间的 cardinality estimates 全部最准，只要求学出来的 statistics configuration 最终帮助 optimizer 做出更好的决策。

这和 5.3.4 的 MNSA 思想其实非常契合。MNSA 本身就是在问：“这个 statistic 导致的 selectivity 信息，会不会改变 optimizer 的 plan decision？”

---

## 11. 两者甚至可以组合，而不是二选一

这可能是最值得继续想的一点。

完全可以做：

$$
\boxed{
\text{Learned Statistics Selection}
+
\text{Learned CE}
}
$$

比如：

```text id="n27h4p"
Historical Workload
        │
        ├──────────────→ Train CE model
        │                     │
        ↓                     │
Learn Stats Config            │
        │                     │
        ↓                     │
Histogram / MCV / NDV         │
        │                     │
        └──────────┬──────────┘
                   ↓
              Hybrid CE
                   ↓
              Cost Model
                   ↓
              Plan Search
```

甚至让 learned CE 的输入不仅是 query encoding，还包括**动态选择出来的 statistics**：

$$
\widehat C
=
f_\theta(q,S^*(W))
$$

这样模型不需要完全从 workload “记住数据分布”，而可以读取 histogram、NDV、multi-column stats 等数据库实际维护的证据。

从统计学习角度，这可能比纯：

$$
q\rightarrow Card(q)
$$

更有结构，因为它把两个东西分开了：

$$
\boxed{
\underbrace{\text{数据库当前的数据分布}}_{\text{statistics}}
+
\underbrace{\text{如何利用这些信息做预测}}_{\text{learned CE}}
}
$$

这样当 **data distribution drift** 时，可以主要 refresh statistics；当 **query workload drift** 时，再调整 statistics selection / CE model。

所以如果把这条思路继续发展，我觉得最值得研究的不是简单地问：

> “learned statistics selection 能不能打败 learned CE？”

而是问：

$$
\boxed{
\text{能否把“学习什么信息值得维护”和“学习如何利用信息做 CE”解耦？}
}
$$

这实际上给了一个很清晰的三层结构：

$$
\boxed{
\text{Workload}
\xrightarrow{\text{learn}}
\text{Statistics Configuration}
\xrightarrow{\text{observe data}}
\text{Statistics}
\xrightarrow{\text{CE}}
\text{Cardinality}
\xrightarrow{\text{optimize}}
\text{Plan}
}
$$

其中第一步学习的是**信息获取策略**，第三步学习的是**预测规则**。这比单纯把整个 CE 做成一个黑盒 \(q\rightarrow Card\) 的视角要丰富得多。
