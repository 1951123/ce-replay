# 5. CE-Replay

CE-Replay is the conceptual center of the method. It turns the supported statistics-sensitive estimator fragment into an executable representation that can be evaluated repeatedly under hypothetical physical statistics states. The physical-design optimizer calls this representation; CE-Replay is not itself the search algorithm, the native estimator, or the complete end-to-end system.

## 5.1 Definition and specialization boundary

Following Definition 2, CE-Replay is a workload-specialized, design-parametric executable representation of the supported statistics-sensitive native cardinality-estimation semantics.

Each part of the definition constrains the method:

- **Workload-specialized.** Query structure, relation context, ordinary selectivity inputs, and other design-independent information are fixed for the supplied workload.
- **Design-parametric.** The selected candidate set and relevant physical realization remain inputs rather than being embedded as one observed outcome.
- **Executable.** Applicability, winner selection, clause consumption, mechanism interaction, and numerical payload updates execute again for each hypothetical state.
- **Native-semantic.** Transition rules are informed by PostgreSQL source semantics and validated against native instrumentation within the supported boundary.

CE-Replay can be viewed as workload specialization of a supported CE fragment: it freezes stable query and relation context while preserving the statistics-sensitive residual program. The current prototype implements mechanisms explicitly using source-informed rules and instrumentation. It does not automatically partially evaluate or compile arbitrary PostgreSQL source code.

## 5.2 Representation decomposition

For each target query, CE-Replay separates four kinds of information.

### Workload-fixed context

The workload-fixed context contains clauses, relation and baseline-cardinality information, ordinary/simple selectivities, compatible predicate semantics, and the semantic dimensions needed by the supported estimator fragment. This context is stable across candidate-selection moves within one frozen realization.

Ground-truth cardinality is retained by the physical-design layer for loss computation. It is not consumed by CE-Replay when reproducing the DBMS estimate.

### Payload and schema context

The frozen repository contains candidate payload values and the schema needed to interpret them. MCV payloads include item values, item frequencies, base frequencies, and dimension ordering. FD payloads include dependency definitions, degrees, and their semantic attribute mapping. Candidate availability is also part of the frozen realization.

Schema order is semantically meaningful. In PostgreSQL MCV payloads, stored dimensions must be interpreted using the statistic's semantic key ordering rather than assuming that textual `CREATE STATISTICS` column order is the payload order. This is a concise correctness example of why a payload cannot be reduced to an opaque scalar candidate response.

### Design-dependent physical state

This state records which candidates are selected and any DBMS-specific realization information that affects semantics. The evaluated PostgreSQL representation retains relevant creation/OID precedence for overlapping MCV ties. Final workload-scale optimization holds the recorded precedence fixed while changing selection.

### Executable semantic state

During one query replay, the program maintains evolving applicability, consumed/estimated clauses, selected MCV rounds, residual selectivity, and FD applicability/contribution state. This state is generated by execution under the hypothetical design rather than copied from one native observation.

## 5.3 Executable control instead of response lookup

A response table could store the winner or estimate observed for one design. Such a table would fail when a candidate toggle changes the winner, exposes a later MCV round, or changes downstream FD applicability. A singleton response model has the same limitation because effects do not compose independently.

CE-Replay instead retains enough semantic structure to recompute those choices. Given a hypothetical selected set, physical realization, payload repository, and workload context, it executes the MCV and FD transition programs described in Section 4. The result is the DBMS estimate for that state, not a prediction of q-error.

The end-to-end chain is:

`physical statistics state → CE-Replay → DBMS cardinality estimate → query loss → workload objective`.

True cardinality enters only at the query-loss step. No separate learned mapping from a statistics design to q-error is needed inside the supported fragment because replay produces the native estimate from which the chosen loss follows directly.

## 5.4 Native reference and supported boundary

Native PostgreSQL instrumentation provides the semantic correctness reference. It exposes raw estimator results at the validated observation boundary so that replay can be compared without conflating semantic error with integer plan-row rounding. Native PostgreSQL is used for semantic validation and final deployment checks; it is not repeatedly called as the final inner-loop oracle for every hypothetical search move.

The validated boundary is PostgreSQL 16.14 statistics-sensitive base-relation estimation for conjunctive restrictions, covering:

- validated scalar predicate forms;
- constant `IN` and `= ANY` ScalarArray MCV semantics;
- multicolumn MCV applicability, GreedyCover, consumption, and numerical combination;
- equality-eligible functional-dependency semantics;
- MCV-first state consumption feeding FD applicability;
- relevant PostgreSQL creation/OID precedence; and
- a supplied payload snapshot with its schema.

The boundary excludes joins, full planner/path search, parameterized paths, arbitrary expressions or operators, general OR/NOT trees, unsupported statistics mechanisms, and arbitrary PostgreSQL versions. “CE-Replay reproduces PostgreSQL CE” is therefore incomplete wording; the method replays the supported statistics-sensitive base-restriction fragment.

## 5.5 Objective-oracle interface

The first interface evaluates a complete hypothetical physical statistics state. For every target query, CE-Replay executes the supported estimator fragment and returns the DBMS cardinality estimate. The physical-design layer applies the frozen query loss and aggregation to obtain the workload objective.

The returned objective is exact with respect to the implemented and validated replay semantics for the supplied frozen payload realization, subject to the documented floating-point tolerance. This statement does not imply exactness for unsupported PostgreSQL semantics or equality between frozen and future fresh payload realizations.

The interface is independent of a particular combinatorial search. Exhaustive enumeration, greedy construction, local search, or another method can invoke the same evaluator as long as it respects the representation's semantic and realization boundary.

## 5.6 Dependency-oracle interface

Executable semantics also expose why and where a candidate matters. CE-Replay records query incidence, semantic dimensions, current MCV control decisions, consumed-clause boundaries, downstream FD applicability, and numerical contribution state. The optimizer uses this information to determine which query/mechanism computations a candidate move can invalidate.

Two dependency notions are required:

- **Realized dependency** records an object or transition exercised by the current trace.
- **Structural or counterfactual dependency** records a potential influence under a candidate toggle, even when the candidate is not currently selected or the current output is unchanged.

The second notion is necessary for correctness. Two current states can have the same estimate or selected winner yet respond differently after adding or removing another candidate. Current-output equivalence is therefore insufficient as a cache key or invalidation proof.

The implementation preserves dependency information needed to evaluate the tested counterfactual moves and falls back to broader replay when a narrower update cannot be justified. Detailed counterexamples show that a compact state sufficient to continue one current execution is not automatically sufficient to restart under arbitrary design extension. This does not rule out state compression; it rules out assuming restart safety from current execution sufficiency alone.

## 5.7 Frozen and fresh realizations

Hypothetical optimization is conditional on the frozen repository. After a design is selected, deployment creates its statistics using the recorded physical realization and runs `ANALYZE`, producing fresh payloads. The fresh realization may change payload values, numerical estimates, or payload availability.

CE-Replay can ingest the fresh payload state and reproduce the supported fresh native estimate. The validation loop therefore separates two questions:

1. **semantic replay error:** whether replay matches native PostgreSQL for the same fresh realization; and
2. **payload realization drift:** whether fresh estimates differ from predictions made with the frozen repository.

An arrow from frozen optimization to deployment must not imply that frozen and fresh payloads are equal. Candidate definitions specify what is created; they do not uniquely determine the payload produced by a future `ANALYZE`.

## 5.8 Interfaces to physical design

CE-Replay exposes two deliberately separate interfaces:

1. the objective oracle returns the workload loss for a hypothetical state within the frozen semantic boundary; and
2. the dependency oracle identifies the query/mechanism state that must be revisited for a candidate move.

The first makes native-semantics-aware design evaluation possible without a separately learned response model. The second makes exact incremental evaluation possible without assuming that every move requires complete workload/control replay. Section 6 describes the concrete maintenance-constrained search that consumes these interfaces.
