# Figure 1 Specification — CE-Replay Physical-Design Pipeline

## Purpose

Figure 1 defines the architecture and the boundary between frozen hypothetical evaluation and fresh physical validation. It must show CE-Replay as a representation/method with two interfaces, while keeping the native estimator, CE-Replay, and physical-design search visually distinct.

## Recommended layout

Use a left-to-right diagram with two horizontal bands.

### Upper band: frozen hypothetical-design loop

1. **Inputs**
   - Supplied target workload
   - Database and workload-fixed CE context
   - Candidate statistic definitions
   - Frozen candidate payload repository
   - Recurring maintenance budget

2. **CE-Replay**
   - MCV applicability and GreedyCover
   - Clause/semantic-dimension consumption state
   - FD applicability and dependency application
   - Numerical CE state and cardinality estimate

   Within the block, draw a directed arrow from the MCV/consumption sub-block to the FD sub-block. Label it “residual estimated-clause state.”

3. **Two explicit interfaces**
   - Objective oracle: estimates followed by workload-loss evaluation
   - Semantic dependency oracle: affected queries, semantic dimensions, and downstream mechanisms

4. **Physical-design search**
   - Contextual marginal-greedy initialization
   - Maintenance-feasibility check
   - ADD/DROP/SWAP local search
   - Incremental move evaluation

5. **Output**
   - Selected physical statistical state
   - Fixed recorded PostgreSQL realization/precedence where relevant

Draw a feedback loop from search to CE-Replay labeled “hypothetical design.” Draw the objective result back to search as “move objective,” and the dependency result back as “incremental invalidation.” Do not label the search block “global optimizer.”

### Lower band: physical deployment and fresh-validation loop

6. **Deployment**
   - Create selected statistics
   - Apply recorded physical realization/order
   - Run fresh `ANALYZE`

7. **Fresh realization**
   - Fresh payload values/schema
   - Fresh payload availability

8. **Fresh CE-Replay**
   - Same supported executable semantics
   - Fresh payload as input

9. **Native PostgreSQL CE**
   - Actual supported statistics-sensitive estimator execution

10. **Comparison**
    - Fresh replay/native semantic error
    - Separately, frozen/fresh payload realization drift when provenance permits

Draw the selected state downward from the upper band into deployment. Draw two separate branches from fresh realization: one into fresh CE-Replay and one into native PostgreSQL CE. Join only their estimate outputs at the semantic-comparison block.

## Visual boundary encodings

- Use a solid enclosing boundary around the frozen hypothetical-design loop.
- Use a second solid boundary around deployment and fresh validation.
- Use a dashed arrow from frozen payload repository toward deployment labeled “candidate definitions selected; payload equality not assumed.” It must not connect frozen payload values directly to the fresh payload box.
- Use different arrow styles or colors for data/context, search/control, dependency feedback, deployment, and validation.
- Include a small annotation beside the frozen repository: “acquired offline.” This prevents an implication that hypothetical payload acquisition is free or solved by CE-Replay.
- Put “supported PostgreSQL 16.14 statistics-sensitive base-restriction fragment” immediately under the CE-Replay title.

## Arrow semantics

| Style | Meaning | Required arrows |
|---|---|---|
| Solid neutral | Data/context flow | workload/context/payload into CE-Replay; fresh payload into fresh replay/native CE |
| Solid control | Search/control flow | proposed hypothetical design from search to CE-Replay; selected design to deployment |
| Dashed feedback | Semantic dependency feedback | affected-query/mechanism state from CE-Replay to incremental search |
| Bold deployment | Physical mutation | selected state to create/order/ANALYZE |
| Paired validation | Same-realization comparison | fresh replay estimate and native estimate into comparison |

## Prohibited implications checklist

The figure must not imply any of the following:

- PostgreSQL source is automatically compiled into CE-Replay.
- Frozen candidate payload equals the fresh payload after deployment.
- Search obtains a global optimum.
- CE-Replay covers full PostgreSQL cardinality estimation or planner search.
- Candidate-payload acquisition is free or generated by the optimizer.
- Native PostgreSQL is called for every hypothetical design in the final inner loop.
- CE-Replay predicts q-error or true cardinality directly.
- Candidate selection universally includes an arbitrary permutation.

## Draft caption

**Figure 1: CE-Replay physical-design pipeline.** For a supplied target workload, workload-fixed estimator context and an offline frozen candidate-payload repository specialize the supported PostgreSQL 16.14 statistics-sensitive base-restriction fragment while leaving design-dependent MCV selection, clause consumption, FD applicability, and numerical updates executable. CE-Replay exposes an objective oracle and a semantic dependency oracle to maintenance-feasible ADD/DROP/SWAP search. The selected physical state is then created with its recorded PostgreSQL realization and analyzed afresh. Fresh payloads feed both CE-Replay and native PostgreSQL for same-realization semantic validation; equality between frozen and fresh payloads is not assumed.

## Figure consistency result

The specification distinguishes the three principal components:

- native PostgreSQL is the semantic reference;
- CE-Replay is the workload-specialized executable representation; and
- physical-design search is the replaceable consumer of replay interfaces.

It also separates semantic replay error from payload realization drift and makes the offline acquisition boundary explicit.
